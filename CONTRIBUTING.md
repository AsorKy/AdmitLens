# Contributing to AdmitLens

Thanks for your interest. AdmitLens is an educational project: one admissions CRM built at four levels of complexity. Contributions are welcome, within the rules below.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Setup

Requirements: `git`, GNU Make 3.81 or newer, Docker, [uv](https://docs.astral.sh/uv/) and Python 3.12.

```bash
make setup    # installs the pinned gitleaks, syncs the guards environment, installs the git hooks and sets local git safety settings
make doctor   # checks that hooks, local git config, gitleaks version and commit identity are in place; prints ok, warn or FAIL, never values
make help     # lists the public targets
```

Run `make setup` before your first commit. It is idempotent, so you can run it again at any time. Everything runs through `make`, locally and in CI.

## The guards

This repository is public, so leaks are prevented in layers:

- a strict `.gitignore`;
- git hooks that scan every commit and every push;
- project-specific detection rules, with their own tests;
- the same scans in CI;
- GitHub secret scanning with push protection.

The hooks check file contents, paths, commit identities and commit messages. A blocked commit or push means the guards found something that must not be published.

**Do not bypass the hooks with `--no-verify`, or by any other means.** In a public repository a pushed secret or personal datum is exposed immediately and cannot be reliably taken back, and CI can detect a leak but cannot prevent it. If a guard flags something you believe is legitimate, open an issue describing it; do not work around it or add an exception on your own.

## Data and secrets

- Never commit data files, `.env` files, keys, tokens, connection strings or any real personal data. This covers raw, derived and seed data alike: no dataset is ever versioned.
- There is no real personal data anywhere in this project, and no real patient data. Names in code, docs, fixtures and seeds are generic.
- Outside the repository, levels 1 to 3 derive their local data from public sources (the SAMHSA TEDS-D and N-SUMHSS datasets, whose facility listings include real establishments, and public web business metadata) plus a synthetic layer. Level 4 and CI use synthetic data only.
- `data/` is git-ignored. Datasets are generated locally and never redistributed.
- Public sources are cited as their terms require; keep that citation in any documentation you add that mentions them.
- Use placeholders in examples, issues and pull requests.

## Commit messages

Commits follow one format, enforced by the `commit-msg` hook:

```
[<State>]{YYYY-MM-DD <PLAN-ID>}: <one-line description>

<optional body: previous state, what was done, expectations>

logs: <names of the audit documents that were updated>
```

- `<State>` is one of: `Pre-Implementation`, `Implementing - N`, `Testing - N`, `Debugging - N`, `Verifying - N`, `Refactoring - N`, `Integrating - N`, `Migrating - N`, `Step-Applied - N`, `Phase-Complete - N`, `Halted - N`, `Post-Implementation`, `Rolled-Back`. `N` is a number.
- `<PLAN-ID>` identifies the plan the work belongs to, as `PLAN-CA-NNNN` or `PLAN-P-NNNN`. Exercises use `KATA-K01` to `KATA-K21`.
- The date is the day of the commit, in `YYYY-MM-DD`.
- The `logs:` footer lists document names only, never paths or links.
- The `commit-msg` hook checks the first line and blocks certain tool-generated trailers. The `logs:` footer and the absence of trailers are conventions that reviewers check.
- `Merge ...` and `Revert "..."` messages generated by git are accepted as they are.
- Commits carry no trailers. The only expected exception is the `Signed-off-by` trailer on Dependabot commits.

Example:

```
[Implementing - 2]{2026-10-18 PLAN-CA-0005}: Add the contributing guide and issue templates.
```

If you are an outside contributor and have no plan to reference, say so in your pull request and a maintainer will tell you which identifier to use.

## How the levels are organized

Each level is self-contained and never imports another level:

```
level-1/backend   level-1/frontend
level-2/backend   level-2/frontend
...
```

The root `Makefile` and the guards never name a level. Only `.github/**` and the `pre-push` hook compose levels. Every `level-N/backend` has its own `Makefile`, `.gitignore` and `.env.example`, and you work inside one level at a time. To compare two levels side by side:

```bash
git diff --no-index level-1 level-2
```

## Running checks

From the repository root:

```bash
make guards-test     # runs the guards test suite
make secrets-scan    # scans the work tree and every commit on every ref
make lint            # lints Makefiles, .gitignore files and workflows
```

For a level, once it exists:

```bash
make -C level-1/backend check
```

Run `make help` inside a level to see its targets. All checks must pass before you open a pull request.

## Pull requests

1. Fork the repository and create a branch from `main`.
2. Make a focused change and keep each commit in the format above.
3. Run the checks listed above.
4. Open a pull request and fill in the template, linking the issue it addresses.
5. CI must be green. Maintainers review, and merge with a rebase, so the history stays linear and each commit message is kept exactly as written.

For larger changes, open an issue first so the approach can be agreed before you invest time.

## Reporting security issues

Never report a vulnerability, a leaked credential or real personal data in a public issue, pull request or discussion. Use GitHub private vulnerability reporting, as described in [SECURITY.md](SECURITY.md).
